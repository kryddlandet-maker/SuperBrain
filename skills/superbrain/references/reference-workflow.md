# From reference to scoped implementation

Inspect the supplied image or live reference before describing its principles. Record source, rights, what was actually viewed, typography roles, composition, light/material behavior, responsive intent and the exact region the user wants changed. A screenshot cannot establish motion; inspect live pointer/scroll states when available.

Keep reference facts, proposed direction and implementation decisions separate in project memory. Derive the visitor task and original concept from the brief. For ordinary third-party references, extract design principles; do not assume permission to copy their content, logos, imagery or code. For a user-supplied vision image that the user explicitly wants reproduced, follow the fidelity workflow below. Asset availability and permissions constrain the implementation.

When a vision image is requested and image generation is available, use that tool and retain the actual output artifact. Otherwise create a rendered HTML/CSS concept. Never call a text description a generated image. The Studio token preview is a real rendered component study; it is not an image-generated vision board or a complete customer site.

For a small CRM sidebar request, target only the marked tab. Preserve row height, text, icon position, route behavior, permissions and the native click target. Place decorative fading dots in a pointer-events:none inner layer clipped to that tab; never replace the sidebar with a hero. Exercise keyboard, touch, interruption and reduced motion. Save before/after screenshots at matching sizes and compare the specific region.

For a complete new site, build actual routes and relevant undersides, with owned assets and honest placeholders only where approved. Validate the implementation against the direction, then record the concrete differences and scoped fixes.

For the machine-readable pipeline, brief.references is an array of source, reviewer, scope (component/page/site), observations, target and preserve fields. Component references require an exact target and preservation list; they select quick-edit unless the user explicitly chooses another mode. The engine records analysis and comparison obligations; it does not claim to have viewed an image merely because a filename was supplied.

## Vision-to-build fidelity workflow

**Trigger:** When the user asks to build a website from an attached, linked, project-stored or just-generated vision image (for example, “build this”, “make it look exactly like the image”), treat the image as the *visual source of truth*, not a moodboard. This instruction is automatic; do not require a separate master prompt, style brief or magic phrase. Explicit requests for inspiration rather than replication stay in the ordinary reference workflow.

1. **Keep the image accessible.** Use the actual artifact in the Codex conversation or a durable project asset (for example, `docs/vision/reference.png`), and record its path plus the original target viewport/aspect ratio. If the actual image is inaccessible, say so and ask for it; do not infer pixel details from a text description or pretend it was inspected. If multiple images conflict, establish which image applies to which page or state.
2. **Inventory observable details before coding.** Note section order, grid, alignment, relative widths/heights, negative space, breakpoints only when shown, heading/body type roles, weights and line breaks, color gradients, contrast, materials, borders, radii, shadows, glows, button states and image/object position/crop. Preserve visible brand content and controls. Treat measurements inferred from pixels as approximate, and use the reference image's viewport.
3. **Implement faithful composition first.** Match overall silhouette, major geometry, typography, assets, color and spacing before polishing microdetails. Do not replace the design with generic sections, cards, decorative labels, counters, alternative imagery or personal “improvements.” Prefer authentic, permitted assets or close licensed substitutes, and document substitutions. Do not rasterize the whole site as one background: preserve semantic, selectable content and working controls.
4. **Fill gaps without inventing image evidence.** One static desktop image does not specify mobile layouts, hover/scroll motion, links, routes, product data or backend behavior. Make restrained, consistent choices for unshown states; respect existing project functionality, touch/keyboard access, reduced motion and responsive layouts. Identify assumptions rather than implying they were depicted in the image.
5. **Visually compare and correct.** Run the implementation, capture a screenshot at the *same viewport dimensions, zoom, state, font availability and ideally content* as the vision image. Inspect both side-by-side or by overlay/diff where tooling permits. Rank discrepancies by impact (section geometry, image placement/crop, typography/line wrapping, backgrounds, spacing, details). Correct and recapture until meaningful differences are addressed; inspect mobile separately without claiming a desktop reference proves mobile fidelity.
6. **Report evidence honestly.** State what matched, what differs, which screenshots/viewports were actually checked, which assets were unavailable, and which interactions remain assumptions or untested. Never promise literal pixel-perfect fidelity or claim automatic visual comparison happened without screenshots and inspection.

**Rights and scope:** A user's own concept/vision image can specify the desired appearance. If it reproduces third-party proprietary marks or assets, do not assume rights to reuse those files; ask for authorized assets or use lawful substitutes. User-requested close visual matching controls art direction, not permission to copy source code or protected media from a third party.
