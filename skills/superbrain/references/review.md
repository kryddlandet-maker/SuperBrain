# Review and learning

Compare rendered work to the actual project brief. Start with composition and visitor tasks: immediate meaning, relevant next action, typography/crop, rhythm, route-specific information and visual continuity. Then inspect input, mobile, focus, motion alternatives and load behavior.

Name concrete defects with route/state and evidence. 'Too generic' becomes useful when explained: every service repeats the same grid, the hero image is irrelevant, or identical spacing makes all content equally important. 'Needs more motion' should identify the intended interaction and benefit.

Use a concise evidence table: criterion, route/input/viewport, observation, artifact, passed/failed/unverified. Keep taste evaluation separate from mechanical checks. Do not convert one user's dislike of gradients into a global prohibition.

For skill changes, compare the same briefs, models, assets and time budget with the previous baseline. Save builds and screenshots, use repeated runs, and ask human reviewers for blind preferences. Include both expressive and quiet business briefs. Record regressions, not only the showcase win. See `benchmarks/README.md` in the source repository.

Before calling a customer site ready, check real submission/booking integration and relevant deployment behavior. A demo does not establish backend readiness. Report limitations precisely.
